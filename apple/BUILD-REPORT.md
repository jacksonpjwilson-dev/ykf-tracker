# Native YKF Arrivals implementation report

Implementation date: November 11, 2026. Repository baseline `7eea9fa`. Branch: `feature/native-ykf-arrivals`. Source implementation is available for review; it is not a signed production release. The follow-up publication commits and pushes this feature branch only. No merge, deployment or production change is authorized or performed. See the branch history and Actions for the final commit/build status.

1. **Existing infrastructure preserved.** All existing `ykf/` modules, config, fleet, Pages files, supervisor/cron scripts, original CI and tracker tests are unchanged against origin/main. Both main and data branches were inspected; the published Pages HTML and live endpoint were read successfully. Arrival detection, provider budgets, shift gating, deduplication and Tower delivery remain the Python backend's responsibility. The original 80 tests passed before implementation and still pass. Operational host, cron, private Firestore writer and calendar credentials are outside this environment; runtime health there was not claimed.

2. **Native iPhone source implemented.** SwiftUI tab navigation, searchable/filterable arrival cards, details, native MapKit with 3/5/10/20/40 NM rings and standard/satellite modes, explicit freshness and uncertainty, monitoring and backend shift display, SwiftData cache/preferences/history, favourites, per-aircraft notification preferences, received-alert centre and local acknowledgement, chart of reported history, CSV export, light/dark/system appearance, Keychain service enrollment, deep links, notification registration, widget cache, App Intents, ActivityKit/Dynamic Island, Watch companion and Watch widget extension. Native controls, semantic text, SF Symbols and scalable fonts are used; device accessibility verification remains pending.

3. **Backend additions.** New opt-in `native_service/` only. An authenticated owner-only FastAPI service reads existing alert-file copies, stores per-device deliveries in SQLite, sends APNs HTTP/2 with ES256 provider authentication, retries transient failures, revokes invalid tokens, records app receipts, filters alert types/muted aircraft and exposes sanitized health counts and owner alert catch-up. The adapter never modifies production queue files or changes alert decisions. It is not started or deployed. No new public coordinate/private-data fields were published.

4. **Branch and files.** Implementation is committed for publication on `feature/native-ykf-arrivals`. Added `apple/` (Swift source, models, tests, checked-in four-target Xcode project and shared schemes, deterministic generator, property lists/entitlements, reused existing Pages app icon and documentation); `native_service/` (service, durable delivery store, API/transport tests, dependencies and deployment instructions); `tests/test_native_delivery.py`; `.github/workflows/native-apple.yml`. The added files preserve existing production files. Full paths and setup are in `apple/README.md`.

5. **Configuration required.** App Group and bundle identifiers/team, target signing and device/simulator setup; server-private APNs key/team/key ID/topic/environment; a TLS gateway, long random owner enrollment credential, read-only alert-root mount, private persistent SQLite directory and service supervision. Enter the HTTPS service URL and credential in the app Settings, grant notification permission and enroll the device. Alert preferences require successful registration. The current service credential model is single-owner; multi-user deployment would need real per-user authorization and device ownership.

6. **Apple Developer requirements.** Membership and appropriate signing profiles/certificates for all four targets, App Group provisioning on each device's app/widget pair, iPhone Push Notifications entitlement, APNs authentication key, and production entitlement/key environment for distribution. Live Activities need system permission and a supported device; Dynamic Island needs compatible hardware. Watch pairing/runtimes and notification behavior must be verified. Xcode 16+ is the intended build environment. Review Watch/app icons and App Store archive requirements before distribution.

7. **Test results.** 95 Python tests passed: 80 original tracker tests plus 15 new delivery/API/mocked APNs tests. One dependency deprecation warning from Starlette's httpx test client, no test failures. An official Swift 6.0.3 Linux toolchain was installed outside the repository; 16 Swift XCTest tests passed, covering real-schema-compatible synthetic decoding, unknown/missing optional fields, distance, freshness/availability, uncertain statuses, Toronto DST/overnight scheduling, cache serialization, stable-ID alert deduplication, history export, deep links, Live Activity policy, invalid positions, ETag/304, fallback and network failure. Actual public live.json additionally decoded successfully in a separate read-only Swift smoke check and correctly classified as stale. No synthetic live operational alert was sent. SwiftData persistence and Apple lifecycle behavior still need device tests; portable serialization tests do not substitute for those.

8. **Xcode results.** Not run: this host is Linux and has no Xcode, Apple SDKs, simulator or signing identity. All Swift source passed the actual Swift compiler's parsing step. The checked-in OpenStep project parsed successfully, all source/asset/plist/entitlement references validated, and regeneration produced identical project/scheme content. These checks do not establish Apple framework type-checking, linking or runtime correctness. A new macOS CI workflow runs portable tests and an unsigned simulator build of the app and dependent extensions; its current remote result is recorded in GitHub Actions after publication.

9. **Operational limits.** Public live.json has no coordinates, groundspeed, heading, callsign/hex, detailed health timestamps or alert history. Map markers therefore remain empty for the current public feed; absent fields are labeled unavailable. No aircraft positions or actual landing times are invented. Operator filtering uses only an explicit backend designation; the public feed suppresses it. Schedule values are estimates, not measured ETAs. GitHub caching/publication delays remain. Native push delivery needs the configured service and Apple infrastructure and is not a safety-critical alarm guarantee. Widgets refresh at system discretion. Local Live Activities update/end during app execution, show staleness when suspended, and have no remote push updates. Watch transfers/haptics are opportunistic. History is local 48-hour publication evidence, pruned during sync, not a global landing archive. EventKit comparison, private position feed/authentication, recovery-event emission, remote Live Activity pushes, richer operational health, continuous off-box watchdog and automatic Head Quarter/G.I.L.E.S. reporting are deferred; no existing infrastructure establishes these capabilities here.

10. **Next development actions.** Open the project on a Mac and run the added CI/build commands; resolve any Apple SDK/compiler findings and verify simulator navigation, real SwiftData persistence, widget families and Watch pairing. Provision signing/App Groups and verify physical-device APNs in sandbox using a separately authorized synthetic test. Review/deploy the isolated adapter behind TLS with the read-only operational queue. Design and privacy-review an authenticated, backward-compatible position/health feed before enabling map aircraft. Then add remote ActivityKit updates, authorized EventKit comparison and Head Quarter integration as separate tested increments. Keep the existing tracker and Tower delivery active throughout rollout.
